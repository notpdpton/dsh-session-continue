# 设计：会话中断继续（dsh-session-continue）

这份文档记录判定规则、wire 契约与代价。它回答的是「为什么这么写」，代码里的注释
回答「这里为什么不能改」。

## 1. 要回答的两个问题

1. 这个会话是不是非正常结束的？
2. 它当时进行到哪儿了（第几轮、任务清单是什么）？

两个问题都由 Host 侧的 `sessionContinueInterruption` 投影回答，浏览器只负责显示。

## 2. 为什么不放在浏览器里折叠

浏览器只持有一个分页的事件窗口——它看得见最近的事件，看不见整条日志。而「日志尾部
有没有一个没闭合的 turn」恰恰是关于**整条日志**的问题。放在投影单元里折叠，框架会
用同样的方式为每个会话计算并缓存它，和自带的 `todos` 等投影走同一条路。

投影**键**是 `sessionContinueInterruption`，带包名前缀。投影键是全局注册的，
两个插件抢同一个键是组合错误而不是合并——像 `interruption` 这种不加限定的名字，
恰好是两个「恢复类」插件都会想要的那种键。

投影单元用 `ctx.sessionProjections.register()` 注册：

```js
{
  key: 'sessionContinueInterruption',
  stateSchema,          // 校验落盘的 checkpoint 行
  init: initialState,   // 每个会话一份全新的初始状态
  apply: foldInterruption,
  wire: { viewSchema, view: wireInterruption },
  stateVersion: 2,      // 折叠语义变化时递增，让旧缓存作废
}
```

## 3. 状态机

`status` 的取值，以及每一个是怎么来的：

| status | 何时 | 客户端 |
| --- | --- | --- |
| `none` | 正常 `completed`；或还没有任何一轮 | 不显示 |
| `crash` | 尾部 `turn/start` 没有对应的 `turn/end`（进程死了） | 显示 |
| `interrupted` | `turn/end { kind: 'interrupted' }`，或非用户主动导致的 `aborted` | 显示 |
| `error` | `turn/end { kind: 'error' }` | 显示 |
| `max-tokens` | `turn/end { kind: 'max-tokens' }` | 显示 |
| `blocked` | `turn/end { kind: 'blocked' }` | 显示 |
| `aborted` | `aborted` 且带 `interrupted: true` 的部分消息（用户按了停止） | 显示，可关 |

`turn/end` 的 `kind: 'interrupted'` **不是**崩溃本身：harness 在恢复一个崩溃的
日志时写这条标记，所以它是审计痕迹而不是实时状态。但正因为如此，**冷读**一个崩溃
会话拿到的 view 一定是 `interrupted`——把它当成「干净结束」会恰好在最该提示的场景
下把提示藏起来。实时的一轮永远不会产生它（只有 `AgentLoop.resume` 会写），所以它不
可能是误报。

`crash` 与 `interrupted` 是同一件事的两种拼写：前者是实时折叠看到的未闭合尾部，
后者是冷读／修复标记／轮间被杀。客户端两种都显示。

## 4. 主动停止与被动中断

这是全篇唯一真正难的地方。

**两种情况的日志字节级一致**：

```json
{ "type": "turn/end", "data": { "turn": 3, "reason": { "kind": "aborted", "reason": { "kind": "user" } } } }
```

用户按停止会写它。Workspace 注册表的 `workspace/session-stop`（归档工作区、应用退出）
也会写它，它调的是 `agent.cancel({ kind: 'user' })`，注释原话是「照用户自己停的样子来」。
**`reason.kind` 本身分不开这两种。**

能分开的是 `partialMessage`：

- 按停止时模型正在流式输出，harness 有东西可以截断，于是把已经交付的前缀以
  `assistant/message { interrupted: true }` 追加进日志；
- 在一轮之间被杀掉（刷新、重启、重连）时没有流在飞，也就没有这条消息。

所以折叠记一个 `partialMessage`，每个 `turn/start` 重置（它只描述当前这一轮），
在 `turn/end` 时用它分流：

```js
status = abortCause === 'user' && state.partialMessage ? 'aborted' : 'interrupted'
```

**默认值偏向 `interrupted`**：误显示一条不需要的提示是无害的，漏显示一条崩溃后的
提示会丢工作。所以只有在**确证**是用户主动停止时才归到 `aborted`。

注意 `aborted` 在客户端默认**也显示**——用户按了停止，活也未必干完。它只是唯一一个
提供开关（「提示手动停止的会话」）的类别。

## 5. wire 契约：引用稳定是硬要求

注册表在相邻两次 `view` 结果按 `Object.is` 不同时发布。一次发布要花掉：

- 一个 Host 控制流帧；
- 一次客户端 store 写入；
- 一次整份会话列表快照重建；
- 一次打开的对话区重渲染。

一轮对话里最常见的两个事件是 `step/start` 和 `step/end`（每个工具调用各一个）。
它们不改变任何客户端会渲染的东西。如果 wire 视图每次重建对象，就会每个工具调用发布两次。

因此：

- `openStep`、`hasTurns` 是 **Host 专属字段**，wire 视图不包含；
- 只有 `step/start`／`step/end` 这两个「只动 Host 字段」的事件走
  `withHostOnlyChange()`，它让新状态**继承上一个状态的 wire 视图对象**，于是
  `Object.is` 相等，不发布。

方向是刻意选的：忘记继承的代价是多一次无害的发布；而把上一份视图带过一个
wire 变化，代价是客户端拿到旧值。

`verify-manifest.mjs` 里有一条对应断言：一轮加 40 个 step 事件，发布次数必须恰好是 1。

## 6. 为什么任务清单要随身带

harness 自带的 `todos` 投影在 `turn/start` 时清空——它回答的是「当前这一轮的计划」。
本投影回答的是「agent 最后记录的计划，也就是要继续做的工作」，所以 `turn/start`
时**刻意保留**上一轮的任务清单。

「继续」把清单塞进消息正文，同样是因为这个：这条消息会开启新的一轮，新的一轮一开始
自带的 `todos` 就空了，模型再也看不到它原本在跟的计划。

清单只在**确实还有没做完的项**时才附带。全部 `completed` 的计划没有可接续的内容，
贴过去只是花上下文复述已完成的事。

## 7. 上限

wire 值会被缓存并推给每个浏览器，所以它是有界的：

- 最多 100 条待办（`MAX_TODOS`）；
- 每条内容最多 300 字符（超出截断并加省略号）。

## 8. 界面的两个状态

提示条有两个形态，横轴对齐要求不同——这里出过一次 bug：

- **收起**：整行作为一个整体垂直居中（`align-items: center`），文字与按钮共用一条
  光学基线，而不是文字浮在上方；
- **展开**：正文从标题往下长，两列都贴顶（`align-items: flex-start`），按钮停在标题
  那一行，而不是漂到详情的中间。

按钮组**不**自己覆盖对齐方式（没有 `align-self`），它跟随卡片的规则。`verify-layout.mjs`
用静态 CSS 审计盯住这条：两态的对齐必须彼此一致，且按钮组不许自作主张。

理由只有一行：提示条收起时只有一行字，用户不该为了一条提示看到文字坐在按钮上半格的位置。

## 9. 显示什么、藏什么

收起时只有一行：状态点 + 标题 + **原因**。原因只是片段（「进程异常退出」），因为标题
已经说了「会话未正常结束」，再写一遍「上次运行……」就是重复。

详情里三行，永远都在：中断轮次、错误代码、错误信息。空值显示「无」而不是消失——面板
形状稳定，读者才能分清「这次结束没有错误代码」和「这个面板不显示错误代码」。

错误代码用等宽字体（是标识符），「无」用正文字体（是散文）。

任务清单**不**在详情里重复：自带的待办面板就在提示条正上方，同一份计划在同一个屏幕上
出现两次是噪音。

## 10. 什么时候不显示

- `status === 'none'`：正常结束；
- agent 正在运行：正在跑的一轮按定义是「打开的」，此时提示是错的；
- 这一次中断已经被「忽略」：忽略按 `status:turn` 记忆，新的一次中断会重新出现；
- 「提示手动停止的会话」关闭且这一轮是用户自己停的。

## 11. 「继续」只能按一次

一条中断只产生一条继续消息。拦两次点击需要两个守卫，缺一不可：

- `busy`（state）拦住「按钮已经 disabled 之后」的点击；
- `submittedRef`（ref）拦住**同一个 tick 内**、React 还没重渲染时的第二次点击——这时
  `busy` 还是 `false`，只看它就会重复提交同一条指令进日志。

latch 在**消息真的进了输入框之后**才落位；提交抛错时保持可重试。按钮落位后显示
「已发送」并保持 disabled，直到出现下一次中断（`status:turn` 变了）才重新武装。

## 12. 本地状态

两个偏好开关存在 `localStorage` 的 `dsh-session-continue:switches` 下。一个极小的
observable 让提示条与设置页共用同一份值：在设置里拨动开关，提示条立刻响应，不需要
刷新。存储读失败或写失败都按「用默认值 / 只改内存」处理——为一个偏好把界面弄挂不值得。

## 13. 配置块放在插件详情页，不占一格导航

两个开关原本是一个独立的 `settings.section`。现在它挪到「插件」页里本插件自己的
详情页，通过 `plugins.bundle.config` 注册，键就是**包名** `dsh-session-continue`。

理由不是省事，而是归属：这两个开关只对这个插件有意义，宿主已经把它的名字、图标、
包名、版本号、启用开关和「包含的组件」都画在那个页面上。再开一个设置分节，等于让
同一个插件的身份出现在两处，还让侧边栏为一个只有两个开关的功能多一格。

键必须是包名而不是 `<包名>#<行 id>`：后者是**某一行**的配置页，本插件的偏好属于
整个 bundle，不属于它的那唯一一行。

页面会问这个条目两次：

| `view` | 用途 | 这里返回 |
| --- | --- | --- |
| `summary` | 一行摘要，仅在包缺少描述时使用 | 一段纯文本 |
| `page` | 详情页里的表单 | 两行开关 |

`summary` 必须是纯文本：它在摘要位渲染，放控件等于把按钮塞进一句话里。

**没有保存按钮。** 每个开关自己就是一次提交，这也正是宿主的行语法对布尔偏好的期望。
页面负责画标题与面包屑，本块只负责行。

块内按宿主自己的度量写，不发明数字：

| 元素 | 规格 |
| --- | --- |
| 行标题 | 14 / 22 |
| 行描述 | 12 / 18 |
| 行内边距 | 16px 上下，一行一条发丝线 |
| 开关 | 36×20 轨道，16px 滑块，2px 内缩，位移 16 |

行右侧用 `padding-right: 48px` 而不是 `space-between`：长描述换行时不会钻到控件下面，
而控件仍然贴着文字。列表最后一行去掉分隔线——这是这一族界面最常见的视觉 bug。

**块里不画标题、包名、版本号。** 详情页已经画了，再画一遍就是把同一个身份在同一屏
上念两次；而版本号一旦在这里存了副本，就只可能过期。`verify-manifest.mjs` 因此断言
浏览器半边既没有标题键，也没有版本常量。

提示条与配置块共用同一份 CSS，因此两处的 token、字号与焦点环只有一处定义。

## 14. 展开详情不画分割线

详情面板在卡片**内部**，就在卡片自己那块表面上往下长。在它上面加一条发丝线，等于把
一张提示切成上下两个盒子——那正是这里被要求移除的那道缝。结构由行网格自己承担，
`.sc-details` 与 `.sc-detail-row` 都不画线。

`verify-layout.mjs` 直接断言这一点：`.sc-details` 没有 `border-top`、没有 `padding-top`，
行本身也没有上下边框，而且整份样式表里不存在任何 `border-top` 声明。最后一条是关键：
它挡的不是「这个类改回来」，而是「换一个类又把线画回来」。

## 15. 名字只写一次

插件的中文名是「会话中断继续」，写在 `locale/zh.json` 的 `meta.title` 里，「插件」页的
卡片标题与详情页标题都读它。

浏览器半边**不再持有这个名字的副本**。它以前有一份，因为那时候它自己画设置页标题；
设置页没了，详情页画名字，那份副本就只可能和真名不一致。现在 `verify-manifest.mjs`
断言浏览器半边里既没有 `settings.title`，也没有 `PACKAGE_VERSION`：不是「两边要一致」，
而是「只许有一边」。

提示条上的标题「会话未正常结束」是另一个字符串，说的是当时的状况，不是插件的名字，
所以它不跟着改名走。

## 16. 宿主版本要求

manifest 声明 `engines.dsh: ^0.2.1-rc.5`。这不是装饰：宿主的 app-boot 兼容闸门在
**导入插件代码之前**读它，落在范围外直接拒绝该行，并在启动器自己的那份组合里标记为
被拒——插件一行都还没跑。

不声明会怎样？看闸门的实现：既没有 `engines.dsh`、也没有 `peerDependencies` 时，
`unmetRequirements()` 直接返回空对象，也就是**无约束**。这个插件在 0.1.x、0.2.0、
将来任何一个版本上都会被默默放行。而它只在 `0.2.1-rc.5` 到 `0.2.2-alpha.3` 这一段上
真跑过。把判断权交给运气，不是声明。

范围的两端都有意义：

- **下界**是实际验证过的宿主，不是"大概能跑"的更早版本。写低了，等于替没有跑过的
  宿主背书。
- **上界**同样是断言。一个没跑过的将来版本不该被默认放进来；要跨过去，用宿主的版本
  豁免（`compatibility.json` 里的 `包@版本 × 宿主版本`，或 `dsh plugin allow-version`），
  那是显式的、逐对授予的、会先打印风险警告的后门。

### 为什么测试自己写了一个范围求值器

这个包没有依赖，而 `verify-manifest.mjs` 必须回答"声明的范围到底放行哪些宿主"。为
一个问题引入 `semver`，会让一个零依赖的插件自己长出依赖——正是它 manifest 里承诺
不做的事。

所以 `test/semver-caret.mjs` 只实现 manifest 允许的**唯一一种**范围形状，而
`verify-manifest.mjs` 遇到别的形状就**拒绝**而不是猜着算。这里踩过一个真的坑：
`^0.2.x` 的上界是 `<0.3.0-0`，不是 `<0.3.0`。少了那个 `-0`，`0.3.0-rc.1` 会被
放进来，而真正的 semver 是拒绝的。这个差异是靠和 npm 自带的 `semver` 逐版本对拍
发现的（18 个版本 × 3 个范围，0 处不一致）；对拍在测试里保留，npm 的 semver 定位
不用写死路径，从 `process.execPath` 推。

## 17. 身份

这个包是独立插件。源码、清单、文案、图标里都不出现其他代码库、其他包名或个人机器
路径。`verify-manifest.mjs` 把这条当作断言在跑，而且它**遍历**仓库里的每个文本文件，
不是读一份手写的清单——新增文件逃避审计，正是这类检查最常见的失效方式。

两条具体的做法：

- 禁止字符串在检查脚本里是**拼**出来的（`['not', 'pdpton'].join('')`），不是写出来的。
  把禁止词原样写在审计里，等于让审计成为那个标识符唯一存留下来的地方。
- 机器路径按**形状**匹配而不是按例子匹配：盘符 + 用户目录、盘符 + 任意顶层目录、
  `file:///` 指向本地目录、写死的 profile 名。产品自己的默认目录 `~/.dsh` 不在名单上
  ——它不含任何个人信息，而一份说明「会话存在哪」的 README 必须能写出它。
